# Mise en place: agent customisation templates

Merge with existing files rather than overwriting them. Replace `<blueprint>` with the blueprint folder name (for example, `blueprint`). Templates below use the GitHub Copilot layout. For other agents, keep the **content** and change the **path and front matter** using this table.

## Platform mapping

| Purpose | GitHub Copilot | Claude Code | Cursor | Tool-neutral |
|---|---|---|---|---|
| Always-on instructions | `.github/copilot-instructions.md` | `CLAUDE.md` (root) | `.cursor/rules/<project>.mdc` with `alwaysApply: true` | `AGENTS.md` (root) |
| Path-scoped instructions | `.github/instructions/<x>.instructions.md` with `applyTo:` | `.claude/rules/<x>.md` with a `paths:` list of globs in the front matter (never a nested `CLAUDE.md` inside source folders) | `.cursor/rules/<x>.mdc` with `globs:` | Nested `AGENTS.md` in the folder |
| Skills | `.github/skills/<name>/SKILL.md` | `.claude/skills/<name>/SKILL.md` | `.cursor/rules/<name>.mdc` (agent-requested, with `description:`) | `.agents/skills/<name>/SKILL.md` |
| Read-only reviewer | `.github/agents/spec-reviewer.agent.md` (`tools: [read, search]`) | `.claude/agents/spec-reviewer.md` (front matter needs `name: spec-reviewer`, `description:` and `tools: Read, Grep, Glob`) | A rule describing the review checklist | A section in `AGENTS.md` |
| Audit scripts | `.github/skills/<blueprint>-traceability-audit/` | `.claude/skills/<blueprint>-traceability-audit/` | `scripts/blueprint/` | `.agents/skills/<blueprint>-traceability-audit/` |

**Links.** Relative links must resolve from the file's own location:
- `.github/skills/<name>/SKILL.md` and `.claude/skills/<name>/SKILL.md` reach the blueprint through `../../../<blueprint>/…`.
- `.github/copilot-instructions.md` uses `../<blueprint>/…`.
- Root `CLAUDE.md` and `AGENTS.md` use `./<blueprint>/…`.

**Several target agents.**
- Skills and the reviewer are generated for **each** target, because each agent only reads its own folder. The scripts are copied into each target's audit-skill folder.
- Always-on instructions:
  - Full content goes in **one canonical file**. This is `AGENTS.md` if it already exists. Otherwise it is the always-on file of the first agent the user named.
  - Every other target's always-on file gets a short **pointer section**: one line linking to the canonical file, plus the non-negotiable principles as a list. The principles are copied deliberately, because they must apply even if the link is not followed.

## Merging with existing files

Never overwrite or reorder existing content.
1. **Always-on files** (`copilot-instructions.md`, `CLAUDE.md`, `AGENTS.md`): keep the existing text verbatim at the top. Append the blueprint sections under one heading, `## Blueprint (generated by mise-en-place)`. If an existing rule conflicts with a blueprint principle, keep both, flag the conflict in the step 12 report and add an `OQ-n`.
2. **Path-scoped instructions and skills with the same name:** add a `-blueprint` suffix to the new file's name rather than editing the existing one, then mention both in the report.
3. **Existing team rules that matter to the blueprint** (for example, "never log note text"): repeat them as principles in the intent, citing the file they came from.

## Optional CI check

```yaml
# .github/workflows/blueprint.yml (or the CI system's equivalent)
- run: python3 .github/skills/<blueprint>-traceability-audit/generate_register.py --blueprint <blueprint> --check --scan src tests
- run: python3 .github/skills/<blueprint>-traceability-audit/check_links.py <blueprint> .github
```

## `.github/instructions/<blueprint>.instructions.md`

```markdown
---
applyTo: "<blueprint>/**/*.md"
description: "Rules for authoring <blueprint> documents."
---
# <Blueprint> authoring rules
- The source document is read-only.
- Keep layers separate (intent / analysis / specs / design / plan / validation). Specs never name classes or libraries.
- IDs `FR|NFR-<PREFIX>-<NNN>` are never reused or renumbered. Withdrawn items are kept.
- EARS wording with a named component as subject. Each row has Pri, Phase and Source.
- ACs `AC-<PREFIX>-<NNN>.<n>` in Given/When/Then form.
- Numbers become `policy:<key>` = default.
- Unknowns become `OQ-n` with a proposed default. Hard-to-reverse decisions become ADRs.
- Use relative links. Regenerate traceability after any spec change.
```

## `.github/skills/<blueprint>-spec-authoring/SKILL.md`

```markdown
---
name: <blueprint>-spec-authoring
description: Create or update a <Project> spec in <blueprint>/02-specs using EARS requirements with stable IDs, priorities, phases, sources and Given/When/Then acceptance criteria. Use when adding, changing, withdrawing or refining requirements.
---
# Spec authoring
1. Ground in intent: the change serves a G-n and violates no NG-n or principle; otherwise stop and raise it.
2. Locate the owning spec via the catalogue. Add a new spec only if no capability owns the behaviour.
3. Cite the source section or add a derived D-n to the analysis.
4. Allocate the next unused ID. Never reuse or renumber.
5. Write in EARS: named component, one behaviour, testable, no implementation nouns.
6. Set Pri / Phase (consistent with the roadmap) / Source.
7. Add ACs (Given/When/Then, concrete values) for every Must.
8. Extract tunable numbers into Policy values.
9. Record unknowns as OQ-n with a default.
10. Propagate to design, ADRs and backlog, then run <blueprint>-traceability-audit.
## Checklist
- [ ] One behaviour, measurable, named subject, source cited, phase consistent, security considered
```

```markdown
1. Check the index. To change a decision, supersede it. Never rewrite history.
2. Take the next number `ADR-NNNN-<kebab-title>.md`.
3. Write Context (forces, IDs, evidence), Decision (active voice) and Consequences (positive, negative, follow-ups).
4. Mark any superseded ADR (change its Status line only). For an extension that doesn't contradict, add `Amends: ADR-XXXX` instead.
5. Update the index, architecture §6 and traceability §2.
## Template
<paste the ADR template from the blueprint's existing ADRs, so the project skill stays self-contained>
```

## `.github/skills/<blueprint>-traceability-audit/SKILL.md` (+ copy `generate_register.py` and `check_links.py` next to it)

```markdown
---
name: <blueprint>-traceability-audit
description: Regenerate and audit the <Project> requirement register in <blueprint>/traceability.md, and find duplicate IDs, Must requirements without acceptance criteria, backlog phase mismatches, broken links, and code or tests that reference unknown or withdrawn IDs. Use after any spec change or before closing a phase.
---
# Traceability audit
1. `python3 <this skill folder>/generate_register.py --blueprint <blueprint> --budget <N> --ac-phases <P0..current phase> --scan <source and test folders>`
   It fails on: duplicate IDs, gated Musts without ACs, backlog items scheduled before their requirement's phase or citing unknown IDs, and code or tests citing unknown or withdrawn IDs.
   It warns on: gated Musts missing from the backlog, and gated Musts with no AC-named test.
2. `python3 <this skill folder>/check_links.py <blueprint> .github`
3. Fix the errors. Explain each warning that remains.
4. Report findings as a table: Severity | ID | File | Finding | Fix. Do not change spec meaning during an audit.
```

```markdown
5. Implement the minimum within the architecture rules and principles.
6. Validate: <build/test/lint commands>.
7. If the design changed, update the spec or design, or add an ADR, in the same change.
8. Update requirement status, run the traceability audit, and use a commit message with IDs.

- <project-specific prohibitions from principles and the security spec>
```

## `.github/agents/spec-reviewer.agent.md`

```markdown
---
description: Read-only reviewer for <Project> <blueprint> documents. Checks specs, ADRs and plans for EARS compliance, testability, traceability, consistency with intent and principles, and security gaps. Reports findings without editing files.
tools: [read, search]
---
# Spec reviewer
Do not edit files. Review against the intent, the spec conventions, the security spec, the roadmap and the ADRs.
## Checklist
1. Intent alignment and scope creep  2. EARS form  3. Testability and ACs  4. ID hygiene
5. Attribution and phase order  6. Numbers as policy  7. Layer separation  8. Security  9. Glossary and link consistency
## Output
Table: Severity (blocker/major/minor) | Location | Finding | Suggested fix, then a verdict: Ready to agree / Needs changes / Rethink.
```
